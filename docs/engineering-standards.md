# 🏛️ ZCode-Plus 高阶工程设计与协同规范 (Engineering Standards)

> 本规范提炼自 Matt Pocock 开源工程哲学（Skills For Real Engineers）及 John Ousterhout《软件设计哲学》，作为 ZCode-Plus 核心补丁注入系统提示词底层，指导 AI 智能体在编码、架构与重构时的设计思维。

---

## 1. 🏛️ 深模块架构设计规范 (Deep Module Design)

> *“最好的模块是‘深’的：用极其简单的接口隐藏庞大复杂的内部实现。” —— John Ousterhout*

### 1.1 深模块 vs 浅模块
* **深模块 (Deep Module - 强烈推崇)**：
  - **小接口 + 厚实现**：对外只暴露极少数的方法和最直观简单的参数。
  - **复杂度就地消化**：接口背后自主消化掉状态流转、并发安全、异常重试、缓存机制等脏活累活。
  - **调用者红利 (Leverage)**：调用方只需学习 1 个方法，就能获取整个系统的完整能力。
* **浅模块 (Shallow Module - 坚决杜绝)**：
  - **大接口 + 薄实现**：对外设计了密密麻麻几十个函数，内部却仅仅做一层无意义的透传、重命名或透出私有数据结构。
  - **认知负担爆炸**：调用方需要了解所有的内部实现细节才能拼凑出一个完整操作。

### 1.2 删除测试 (The Deletion Test)
衡量代码库中任何一个类、模块或包是否有存在价值的黄金法则：
* **伪抽象（浅模块）**：如果尝试删除该模块，系统的复杂度并没有增加，甚至很多啰嗦的中间层直接消失了——说明该模块是无用的纯噪音，应当立刻剔除。
* **真抽象（深模块）**：如果尝试删除该模块，其原本承担的复杂边界、重试、持久化与校验逻辑瞬间分散蔓延到全系统几十个调用点——说明该模块具有极高的深模块价值。

### 1.3 可测试性设计 (Design for Testability)
1. **显式依赖注入**：通过参数或构造函数接收依赖，严禁在内部隐式写死 `new Service()`。
2. **纯函数优先**：优先设计“输入数据 ➔ 返回计算结果”的数据管线，避免隐藏的全局或对象内隐式副作用。
3. **接口即测试边界**：单元测试只针对公开的深模块接口进行黑盒验证，严禁越过接口去打探私有状态。

## 2. 🌲 决策树质询与需求对齐规范 (Design Tree Alignment)

> *“软件工程最惨痛的浪费，是把根本不需要的东西高保真地实现出来了。”*

### 2.1 拒绝主观臆测
在遇到以下情况时，AI 严禁凭空假设用户偏好或私自拍脑袋决定：
* 存在多种明显不同的技术架构选型（如 SQLite vs JSON、轮询 vs 事件驱动）；
* 涉及破坏性或向下不兼容的重构；
* 核心需求描述存在模糊或多重语义解释。

### 2.2 决策树建模 (Decision Tree)
1. **树形分支展开**：将待定决策拆解为相互依赖的“设计树”。
2. **按轮次推进 (Rounds & Frontier)**：优先定位阻断下游所有步骤的核心前置问题。
3. **提供推荐选项 (Recommended)**：提出每个问题时，必须附带 AI 的专业推荐选项与技术理由，降低用户决策心智负担。
4. **事实先查后问**：凡是能通过代码搜索、阅读文件、执行终端命令查清的客观事实，AI 必须先自行查证，绝不向用户提问琐碎事实。
